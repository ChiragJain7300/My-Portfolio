1. BLANCA — Real Estate Discovery & Management Portal
--------------------------------------------------------------------------------
Tech Stack: Next.js 16 (App Router / SSR), React 18, NestJS 11, PostgreSQL, TypeORM, TanStack React Query v5, Redux Toolkit, Material React Table

• Resume Bullets:
  - Architected a decoupled real estate platform using Next.js 16 and NestJS, achieving sub-200ms page transitions with TanStack Query caching across 500+ property listings.
  - Engineered an isolated lead ingestion pipeline that syncs customer inquiries to PostgreSQL and Buildesk CRM, maintaining 100% lead capture during third-party CRM downtime.
  - Built an administrative drag-and-drop property reordering table using @dnd-kit and batched SQL updates, reducing database write operations by 90%.

• How to Explain the Numbers in an Interview:
  - "Sub-200ms page transitions":
    "On the public portal, users frequently toggle between property listings and filters. TanStack React Query caches visited queries in browser memory. When a user navigates back to a previously loaded project or filter view, the data renders instantly from cache without waiting for a new backend request."
  - "100% lead capture":
    "Previously, if the external CRM had high latency or was down, user submissions could fail. I separated the flow: when a user submits an inquiry, we commit it to our local PostgreSQL database first, return success to the user, and then dispatch to Buildesk CRM in an isolated background block so external downtime never loses a lead."
  - "90% fewer database writes":
    "When admins reordered featured properties, a naive implementation would send an update request for every single item moved. Instead, we update the UI instantly, collect the new sequence array, and send a single batch array [{ id, sequence }] to the backend to update all items in one database transaction."

5. WDM PLATFORM — E-Commerce Warehouse & Data Synchronization
--------------------------------------------------------------------------------
Tech Stack: Node.js (ES Modules), Express.js 5, MongoDB, Mongoose v8, node-cron v4, Bol.com Retailer API v10, Monday.com GraphQL API

• Resume Bullets:
  - Engineered an automated e-commerce data pipeline in Express.js 5 and MongoDB, reducing redundant OAuth roundtrips by 98% through a database token cache with a 30-second pre-expiry buffer.
  - Maintained 100% catalogue consistency across Bol.com listings by designing a set-difference reconciliation algorithm that automatically deletes delisted products from the database.
  - Formulated a self-healing morning cron architecture that automatically retries only failed jobs at 7:00 AM, saving ~1.5 hours of daily manual engineering maintenance.

• How to Explain the Numbers in an Interview:
  - "98% reduction in OAuth calls":
    "Our scheduled morning cron jobs make dozens of API requests across products, stock, and advertising. Bol.com access tokens last for several minutes. Instead of requesting a new token for each sub-task, we store the token in a MongoDB collection with an expiry timestamp minus 30 seconds. Every task reuses this valid token, only making an OAuth network call when the token has actually expired."
  - "100% catalogue consistency":
    "When a seller removes a product on Bol.com, that product simply vanishes from the daily CSV export. If you only do 'upserts' on incoming rows, deleted products remain in your database forever. After upserting active rows, my script compares all stored EANs against the incoming CSV's EAN set and deletes any items not in the CSV."
  - "Saving ~1.5 hours of manual maintenance daily":
    "Previously, if a third-party API had a 30-second network timeout during the 4:00 AM run, a developer had to wake up, check the logs, and manually re-run the failed scripts. I added a 7:00 AM recovery cron that inspects the CronLog collection for tasks marked with ❌ that morning, retries only those failed tasks, and updates the log to ✅ on success."

6. VERIFIED INBOX (SCREEN) — Gmail Intelligence & Sender Security Platform
--------------------------------------------------------------------------------
Tech Stack: NestJS 11, TypeORM, PostgreSQL, React 19 (Vite 7 + React Compiler), TanStack React Query v5, Tiptap v3, Google OAuth 2.0

• Resume Bullets:
  - Built a Gmail security and inbox intelligence platform in NestJS 11 and React 19 that synchronizes 500+ emails in under 6.5 seconds using parallel batches of 50 concurrent API requests.
  - Eliminated OAuth token refresh race conditions by implementing a Promise-coalescing lock map, preventing Google invalid_grant errors and user session logouts during concurrent syncs.
  - Designed an atomic, single-use authentication code exchange (DELETE ... RETURNING) that resolved cross-origin SameSite cookie drops on Google OAuth redirects.

• How to Explain the Numbers in an Interview:
  - "500+ emails in under 6.5 seconds":
    "Fetching full email payloads sequentially over HTTP is slow. When doing the initial sync, we list message IDs and then fetch full RFC822 payloads in parallel batches of 50 using Promise.allSettled. This gives high throughput without exceeding Google's per-second rate limits."
  - "Promise coalescing to prevent invalid_grant":
    "When a user opens the inbox, multiple background syncs and UI widgets fire at once. If the token is expired, all callers detect expiry at the same time and attempt to call Google's refresh endpoint. Google invalidates old refresh tokens upon first use, so the second call fails and logs the user out. With a Map<userId, Promise<string>>, the first caller creates the refresh promise, and all other callers await that exact same promise."
  - "Atomic single-use auth code exchange":
    "Setting an httpOnly session cookie during a 302 cross-origin redirect from Google fails in many modern browsers due to SameSite restrictions. Instead, the backend generates a 2-minute UUID code in auth_code_exchange and redirects the user to /login?code=UUID. The frontend calls /auth/exchange, and the backend runs DELETE ... WHERE code = :code RETURNING user_id. This validates and deletes the code in a single SQL operation, making it impossible to reuse."
